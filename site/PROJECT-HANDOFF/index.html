Persian/Arabic don't inherit Instrument Serif because the :lang() rule wins the cascade and overrides font-family back to IRANSans / IBM Plex Sans Arabic.

7. Form / apply behavior

The /apply, /fa/apply, and /ar/apply forms all behave identically aside from language:

Behavior Detail
Component src/components/apply/ApplyForm.tsx — the only "use client" component in the project
Submission target mailto:iranfluent.com@gmail.com
Email subject AI Transformation Review Application (universal English, all locales)
Email body Localized to the page's locale — labels in fa / ar / en match what the submitter saw
Visible fallback "Or email us directly at iranfluent.com@gmail.com." with the email as a clickable mailto link
State management Single useState<FormState> object; 10 fields total
Validation HTML5 — required on Name / Email / Company / "What do you want AI to help with?" / Consent; type="email" and type="url"; maxLength={1000} on the three textareas
Default language radio First option of the locale (English on en, Persian on fa, Arabic on ar)
Form fields Name; Email; Company or project; Website (optional); 3 textareas (help-with / existing / bottleneck); Interests (multi-checkbox: 4 service categories); Preferred language (radio: 3 options); Consent (required)
No backend No API routes, no server actions, no database, no CMS, no auth. Form data only exits the user's machine when they send the prefilled email from their mail client.

8. Known limitations

  1. <html lang> and root dir are always lang="en" with no dir attribute at the root layout. Persian and Arabic routes get RTL via a nested <div lang="..." dir="rtl"> in src/app/fa/layout.tsx and src/app/ar/layout.tsx. Search engines and assistive tech would benefit from correct root-level attributes — requires per-locale root layouts.
  2. Mobile navigation hides anchor links at <sm breakpoint (hidden sm:flex). Phone visitors only see the wordmark + language switcher. No hamburger menu.
  3. Language switcher always links to homepages (/, /fa, /ar), not the equivalent apply route. A visitor on /fa/apply clicking "العربية" lands on /ar, not /ar/apply. Locale-aware path mapping is a future improvement.
  4. Translations are V1 quality — Persian and Arabic content was translated directly rather than reviewed by a native speaker. Acceptable for V1; flagged for native review.
  5. No submission tracking by design (no backend). The site can't observe whether a user actually sent the prefilled email.
  6. mailto: URL length — with Persian/Arabic content and three 1000-char textareas, the URL can exceed 20-30 KB. Most modern mail clients handle it; legacy Windows configurations may truncate. Visible fallback email line is the explicit Plan B.
  7. Diagnostic numerals stay Latin (01–05) in all locales for visual consistency with the home Problem section. Persian/Arabic readers see Latin digits in the Diagnostic prefix.
  8. mailto subject is universal English — recipient-friendly for inbox filtering, but submitters see English text in their mail composer subject line.
  9. No focus-visible rings on form inputs — relies on browser defaults. A consistent focus-ring policy is a future a11y polish item.
  10. public/fonts/ ships unused IRANSans weight directories (Light, UltraLight, Black, the (FaNum) variant tree, the original IRANSans.zip, the WebFonts.png preview). These aren't referenced by CSS but are publicly accessible at /fonts/... URLs. Cleanup is a small future task.
  11. No Open Graph / social meta tags — link previews on Slack/LinkedIn/iMessage use Next's default behavior.
  12. No sitemap.xml or robots.txt — light SEO items.
  13. AgentSpotlight is the only dark surface on every page. Intentional; no visual variety pattern beyond it currently.

9. Phase 4 backlog

In rough priority order:

  1. Translation review — native-speaker review of all Persian and Arabic copy, especially the /apply flow and form labels.
  2. Locale-aware LanguageSwitcher — when on /fa/apply clicking another language should land on the equivalent apply route in that language, not the homepage.
  3. <html lang> and dir per locale at the root layout — requires either per-locale root layouts or a dynamic root layout. Improves SEO and a11y signaling.
  4. Mobile navigation — small hamburger menu or section anchor dropdown so phone visitors can navigate without scrolling through every section.
  5. Open Graph + social meta — per-locale og:title, og:description, og:image. The icon.svg could be the basis for a 1200×630 OG image.
  6. Sitemap.xml + robots.txt — light SEO.
  7. Submission tracking — privacy-friendly analytics event on the submit handler (Plausible, Vercel Analytics) to observe conversion.
  8. Real Resources content — the homepage Resources teaser still says "First writeups coming soon." Ship the actual first writeup.
  9. Diagnostic numerals localization — lift 01–05 into per-locale number fields so fa shows ۰۱–۰۵ and ar shows ٠١–٠٥.
  10. mailto subject localization — per-locale subject would let submitters see a familiar string in their compose window. Trade-off: recipient-side filtering becomes locale-aware.
  11. Long mailto fallback — copy-to-clipboard button that generates the same body text, for edge cases where the prefilled compose window fails.
  12. Focus-visible rings — global focus-visible:outline-2 focus-visible:outline-accent focus-visible:outline-offset-2 on interactive elements for clearer keyboard-only navigation.
  13. public/fonts/ cleanup — delete the unused IRANSans weight directories, the (FaNum) tree, the original .zip, and the WebFonts.png preview to slim the deployed artifact.
  14. Founder photo / signature — only if/when the founder is ready to add it; current restraint is intentional.
  15. AgentSpotlight pattern reuse — if a second contained dark moment is wanted elsewhere, the rounded-2xl bg-inverse text-white pattern is reusable.

10. How to run / build / deploy locally

Prerequisites

  • Node.js 20+
  • npm (project uses npm — no yarn / pnpm)

Install

git clone https://github.com/hiwasham/AITransforms.git
cd AITransforms
npm install

Develop

npm run dev
# Open http://localhost:3000
# Routes: /, /fa, /ar, /apply, /fa/apply, /ar/apply

Verify

npm run build        # Next.js static build (Turbopack)
npm run lint         # ESLint
npx tsc --noEmit     # TypeScript typecheck

All three commands must pass cleanly before pushing.

Deploy

  • Production: push to main. Vercel auto-deploys to v1.aitransforms.ir.
  • Preview: push any other branch. Vercel auto-generates a preview URL (also visible in GitHub PR checks).
  • No environment variables required. No Vercel build overrides needed. The Next.js auto-detection on Vercel handles everything.

Adding content

  • Homepage copy → src/content/site.ts (locale-keyed: en, fa, ar).
  • Apply page copy → src/content/apply.ts (locale-keyed).
  • Both files use as const so each locale's literal type aligns across the union. Adding or removing a field in one locale requires the same change in the other two.

Adding a route

Place a page.tsx under src/app/<route>/. Static generation is automatic. For a localized route, place it under src/app/fa/<route>/ or src/app/ar/<route>/ — it inherits the parent layout's dir="rtl" and lang attributes.
