# Design: Public, Login-Protected Outreach Operator Dashboard

Generated by `/office-hours` on 2026-07-27
Branch: `feature/warm-gift-outreach`
Repo: `hiwasham/AITransforms`
Status: APPROVED
Mode: Startup / internal operator infrastructure

## Problem Statement

The outreach operator dashboard exists and works only as part of a localhost-oriented, long-running Node service. Hiwa cannot reliably open the real dashboard from another browser or device, and publishing the current runtime unchanged would expose prospect data plus approve, reject, import, generation, dispatch, and webhook surfaces without authentication.

The goal is a real browser-accessible operator dashboard, not a static mock. It must preserve PGlite data across restarts while keeping every operator UI and review API route unavailable to unauthenticated visitors. The first public runtime is deliberately dashboard-only; unrelated engine routes are not registered on its listener.

## Demand Evidence

- The operator explicitly requested a public browser link and repeated the request after the marketing site deployment.
- The dashboard, review queue, decision APIs, persistent schema, and tests already exist. The missing capability is safe remote access and reliable process hosting.
- The operator selected a public Tailscale Funnel URL with an application login over the slower Google SSO/domain path and the non-public tailnet-only path.

## Status Quo

- `outreach-engine` is a separate Node service with a plain HTTP server and static dashboard UI.
- The runtime is designed for a Linux host and persistent PGlite directory.
- The server has no authentication or browser session boundary.
- The approved specification binds the service to localhost and explicitly makes authentication a prerequisite for public exposure.
- Vercel is suitable for the static marketing site but not this service's persistent disk, Telegram long polling, or long-lived process.
- Dispatch remains `MockDispatchClient`; real provider sending is not implemented.

## Target User & Narrowest Wedge

The only operator in the first release is Hiwa. The narrowest useful release is:

1. One public HTTPS URL on a new Tailscale Funnel port.
2. One operator login backed by a secret stored in Infisical and injected at runtime.
3. The existing review dashboard and review routes protected by the same authenticated session, except the login/logout endpoints and an intentionally minimal health endpoint.
4. Persistent PGlite storage on the Finland VPS.
5. No Telegram, generation, provider webhook, prospect, or dispatch route registered on the public listener. The runtime refuses to start unless configured as `dashboard` + `mock`.

## Constraints

- Keep `outreach-engine` isolated from the Next.js marketing site.
- Do not deploy the long-running service to Vercel serverless.
- Bind the Node process to loopback; Tailscale Funnel is the only public ingress.
- Store credentials in Infisical, never in Git or plaintext project files.
- Use a secure, HTTP-only, same-site session cookie over Funnel HTTPS.
- Reject unauthenticated access to UI, reads, and mutations.
- Reject cross-site mutation requests with an Origin check and require JSON content types for JSON APIs.
- Do not register webhook, batch, prospect, Telegram, or internal dispatch surfaces in the public dashboard runtime.
- Require explicit dashboard runtime and mock dispatch modes at startup; fail closed on any other value.
- Back up Tailscale, service-manager, and proxy configuration before writes.
- Preserve the active branch's unrelated untracked files.

## Premises

The operator explicitly agreed to these premises:

1. This is the real service with persistent data, not a static dashboard preview.
2. The first public release is login-protected.
3. The service runs on the existing Finland VPS as a long-lived process.
4. Sending remains mechanically unavailable in the first public release.
5. The initial public URL does not wait for `aitransforms.ir` DNS repair.

## Approaches Considered

### Approach A: Tailscale Funnel + application login

Run the existing service under systemd, bind it to loopback, expose a new Funnel HTTPS port, and add a small session-auth boundary inside `outreach-engine`.

- Effort: medium
- Risk: medium
- Pros: public URL now, persistent runtime, no DNS dependency, one deployable service, testable authentication boundary.
- Cons: adds security-sensitive application code and a non-default port to the public URL.
- Reuses: existing Node server, selected existing review handlers, static UI, PGlite store, Finland host, Tailscale TLS.

### Approach B: Cloudflare Access + Google SSO

Keep the service on the VPS and put Cloudflare Tunnel/Access with Google login in front of it.

- Effort: large
- Risk: medium
- Pros: polished social login and centralized identity policy with little application auth code.
- Cons: blocked on domain/DNS ownership, Cloudflare configuration, and OAuth setup; introduces a second infrastructure vendor.
- Reuses: existing service and host, but replaces Tailscale as public ingress.

### Approach C: Tailscale Serve only

Expose the service only inside the private tailnet and rely on Tailscale identity.

- Effort: small
- Risk: low
- Pros: strongest network isolation and almost no application auth surface.
- Cons: does not satisfy the explicit public-internet requirement and requires Tailscale on every viewing device.
- Reuses: current private Tailscale Serve configuration.

## Recommended Approach

Use Approach A. It is the only path that satisfies public browser access now without depending on broken external DNS or adding Cloudflare. The application boundary is intentionally small: login, logout, session verification, secure-cookie handling, cross-site mutation rejection, and protected routing.

The runtime topology is:

```text
Browser
  -> Tailscale Funnel HTTPS on a new port
    -> 127.0.0.1:<outreach-port>
      -> authentication boundary
        -> existing UI and route table
          -> persistent PGlite directory
```

Implementation must keep login/session logic separate from outreach domain logic. A dedicated dashboard composition root registers only the route matrix below. It receives an auth dependency and protects routes at the outer request boundary before route dispatch. The credential is compared in constant time. The session cookie contains no prospect data and follows the exact contract below.

### Authentication contract

- Login is password-only for the single operator. There is no username field and therefore no account-discovery response.
- `GET /login` returns a self-contained HTML form with no separate public JavaScript or stylesheet.
- `POST /login` accepts only `application/x-www-form-urlencoded`, with a maximum body size of 4 KiB and one field named `password`.
- Success returns `303 /`, issues `__Host-outreach_session`, and never reflects or logs the password.
- Every credential mismatch returns the same fixed `401` response. Malformed form data returns fixed `400`; a body over 4 KiB returns `413`; a non-form content type returns `415`; a limiter block returns `429`. None includes credential or route detail.
- The cookie has `Path=/`, no `Domain`, `HttpOnly`, `Secure`, `SameSite=Strict`, and a 12-hour absolute (not sliding) lifetime.
- The stateless session payload contains only version, issued-at, expiry, and 128 bits of random nonce. It is base64url-encoded and authenticated with HMAC-SHA-256 using a separate signing secret.
- Invalid format, signature, version, or expiry is rejected in constant time where a secret comparison occurs.
- Service restarts do not invalidate unexpired sessions. `POST /logout` clears the browser cookie but cannot revoke a copied stateless token before its absolute expiry; this limitation is accepted for the single-operator first release.
- `POST /logout` is same-origin protected, accepts a missing/invalid session, always clears the cookie, and returns a fixed `303 /login`.
- The operator password is generated from at least 16 random bytes (128 bits) and the signing key from exactly 32 random bytes. Startup decodes and validates both minimum strengths before listening.
- The configured password is reduced to a fixed-length SHA-256 digest at startup; each bounded candidate is digested and compared with `timingSafeEqual`. The raw configured password is never retained outside the injected environment value and is never persisted by the application.

### Login abuse controls

- The HTTP bridge caps every request body at 1 MiB before buffering; login has the stricter 4 KiB limit.
- Failed login attempts use an in-memory global limiter: at most 50 credential failures in 15 minutes, followed by a 15-minute block. A strong random password makes this a traffic-abuse guard, not the primary credential defense.
- The first release discards `Forwarded`, `X-Forwarded-For`, and similar client-IP headers for security decisions because Funnel's append/preserve behavior has not yet been verified against spoofed input. A per-source limiter may be added only after a controlled preflight proves which proxy-added hop is trustworthy.
- Rate-limit responses are fixed `429` responses with no credential detail. Logs contain only event type, time, and global limiter state.
- Reset-on-restart is accepted because the global limit is defense in depth behind Funnel HTTPS and a 128-bit-or-stronger password, but repeated service restarts are separately visible in journald.

### Exhaustive route matrix

Unclassified method/path pairs fail closed with the existing generic `404`; protected-resource existence is never disclosed to unauthenticated callers.

| Class | Method and path | Policy |
|---|---|---|
| Public auth | `GET /login` | Self-contained login page; `no-store` |
| Public auth | `POST /login` | Same-origin, form-only, rate-limited |
| Public auth | `POST /logout` | Same-origin; always clear cookie |
| Public health | `GET /healthz` | Fixed `{ "status": "ok" }`; no dependency/version/path details |
| Operator UI | `GET /` | Missing/invalid session redirects `303 /login` |
| Operator asset | `GET /ui/review.js` | Missing/invalid session returns fixed `401` |
| Operator API | `POST /review/imports` | Session + origin + `application/json` |
| Operator API | `GET /review/packages/next` | Session required |
| Operator API | `GET /review/packages/:id` | Session required |
| Operator API | `POST /review/packages/:id/decision` | Session + origin + `application/json` |
| Operator API | `POST /review/packages/:id/rejection-reason` | Session + origin + `application/json` |
| Not registered | `/batches/**`, `/prospects/**`, `/internal/**`, `/webhooks/**` | Fixed `404` in dashboard runtime |

The canonical allowed origin is an exact `OUTREACH_PUBLIC_ORIGIN` HTTPS value obtained from the enabled Funnel URL. It is never inferred from `Host`, `Forwarded`, or `X-Forwarded-*`. Every state-changing public/operator request must match this origin. Login, logout, protected responses, protected redirects/errors, and review APIs send `Cache-Control: no-store`.

The response security policy is `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'unsafe-inline'; connect-src 'self'; img-src 'self'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`, plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and no permissive CORS headers.

Logs record authentication and review audit metadata without the submitted credential, cookie, session token, prospect text, message content, or secret. Safe review audit fields are package ID, action, reason enum when present, timestamp, a random per-session audit identifier, and `dispatch_mode=mock`.

## Runtime and Secret Delivery

- The public release requires `OUTREACH_RUNTIME_MODE=dashboard` and `OUTREACH_DISPATCH_MODE=mock`; startup fails for missing or different values.
- Dashboard mode constructs only the DB, auth boundary, static dashboard, health route, and review route handlers. It does not construct LLM, Telegram, webhook, prospect, batch, or dispatch clients.
- The UI displays a persistent `SIMULATION MODE — nothing will be sent` banner. Startup and decision audit events include `dispatch_mode=mock` using IDs only.
- Application secrets remain in Infisical. The systemd unit never contains secrets and has no plaintext `EnvironmentFile`.
- The unit uses `LoadCredentialEncrypted=infisical-client-id:...` and `LoadCredentialEncrypted=infisical-client-secret:...`; systemd decrypts them only into `$CREDENTIALS_DIRECTORY` for the service.
- `ExecStart` calls a root-owned, non-writable `/usr/local/libexec/aitransforms-outreach-start` wrapper. The wrapper uses `set -eu` and never shell tracing, reads the two credential files into the Infisical CLI's documented Universal Auth environment inputs, captures the short-lived login token without printing it, unsets the bootstrap values, and `exec`s `infisical run` for the pinned release command. Application secrets are injected directly into the final child environment on every service start.
- If credential decryption, Infisical authentication, secret retrieval, or required-secret validation fails, the wrapper exits before Node starts. Preflight must validate the installed CLI's exact Universal Auth flags/environment names; unsupported CLI behavior is a deployment blocker, not a reason to place a secret in an argument or file.
- Secrets are forbidden in command-line arguments, release directories, unit text, Git, shell scripts, persistent environment files, and journald. The bootstrap procedure validates redaction before enabling restart.

## Persistent Data and Release Lifecycle

- Dedicated service user/group: `aitransforms-outreach`; no login shell.
- Durable PGlite directory: `/var/lib/aitransforms-outreach/pglite`, owned by the service user, mode `0700`, outside all code releases.
- Exactly one writer is enforced by one systemd service plus a held `flock` for the process lifetime. A second instance fails before opening PGlite.
- systemd uses `Restart=on-failure`, `KillSignal=SIGTERM`, and `TimeoutStopSec=30`. The existing graceful shutdown closes HTTP, PGlite, and any enabled transport; dashboard mode has no Telegram transport.
- Releases are immutable directories `/opt/aitransforms-outreach/releases/<git-sha>` with an atomic `/opt/aitransforms-outreach/current` symlink. `WorkingDirectory` and `ExecStart` resolve through `current`.
- Release directories and the `current` symlink are root-owned and not writable by `aitransforms-outreach`. The service account can write only its PGlite directory and its systemd-created runtime directory.
- Schema application remains idempotent at startup. This release adds no DB migration. Future incompatible migrations must block code rollback or supply a tested down/forward recovery path.
- A consistent backup is offline for this release: stop the unit, verify no lock holder, archive the durable data directory with ownership/mode metadata into `/var/backups/aitransforms-outreach`, restart, and verify health. The backup directory is root-owned `0700`; archives are `0600`; the newest 7 successful local backups are retained. Any off-host copy must be encrypted to the designated `age` public recipient before transfer. Restore is first tested against a separate temporary PGlite directory, then documented with the exact backup identifier.
- Code rollback order is: disable the new Funnel entry, stop service, point `current` to the previous compatible release, start service, verify private health/login, restore Funnel entry, then verify public health. Data is restored only for a demonstrated data problem, never as part of routine code rollback.

## Funnel Preflight and Rollback Gate

Observed state before implementation: Tailscale `1.98.9`; existing HTTPS Serve entries occupy the default HTTPS endpoint and port `10000`; no public Funnel entry is active. Port `8443` is preferred but not yet assumed free or policy-enabled.

Before enabling ingress:

1. Capture timestamped `tailscale serve status --json`, `tailscale funnel status`, active listeners, installed Tailscale/systemd versions, encrypted-credential capability, and the relevant unit state.
2. Prove `systemd-creds` host-bound encrypt/decrypt works and validate the installed Infisical CLI Universal Auth flow without leaking values to process arguments, persistent files, or journald. Failure blocks this deployment mechanism.
3. Verify `8443` is free, Funnel-supported, and allowed by tailnet policy. If not, stop and revise the design; do not reuse or replace an existing endpoint.
4. Read the node's canonical Tailscale DNS name from local status JSON and deterministically construct `https://<canonical-dns-name>:8443` as `OUTREACH_PUBLIC_ORIGIN` before starting the production-configured service. Confirm the later Funnel-reported origin matches exactly.
5. Start the dashboard on loopback with the final canonical origin and pass local login/auth/data/restart checks using explicit matching/mismatching Origin headers.
6. Normalize the captured existing Serve endpoint definitions by listener, path, proxy target, and exposure mode. Add only the new Funnel entry and verify the normalized pre-existing definitions remain unchanged; ignore output ordering and incidental status fields.
7. Verify the reported public URL from a browser and confirm it exactly matches `OUTREACH_PUBLIC_ORIGIN`.
8. Exercise rollback by removing only the new entry, confirm normalized prior endpoints remain unchanged, then re-add the verified entry.

## Success Criteria

1. An unauthenticated browser receives the login page and cannot read dashboard HTML, JavaScript, prospect data, or API responses.
2. Invalid credentials fail without revealing whether the username or secret was wrong and without placing secrets in logs.
3. A valid login creates a secure, HTTP-only, same-site, signed, expiring session; logout invalidates it in the browser.
4. Every operator UI/API route rejects missing, invalid, expired, or tampered sessions.
5. Cross-origin state-changing requests are rejected; JSON APIs reject unsupported content types; oversized bodies fail before buffering beyond the configured cap.
6. Every unregistered engine route, including webhook and internal dispatch paths, returns the generic `404` from the dashboard runtime.
7. The Node process binds only to loopback and restarts under systemd without losing PGlite data.
8. Tailscale Funnel exposes only the chosen service port and has a captured rollback configuration.
9. Startup refuses non-dashboard/non-mock modes, no external integration client is constructed, the simulation banner is visible, and a verified decision performs no external network transport.
10. Unit, contract, integration, typecheck, and live browser QA pass.
11. The final public URL opens from a browser, requires login, renders the real queue after login, shows no console errors, and survives a service restart.
12. Rate limits, cookie tampering/expiry, direct protected-asset access, fixed unauthorized responses, CSP/framing headers, and logout behavior have automated coverage.
13. A backup restores successfully into a separate PGlite directory, and the service retains real records across stop/start.

- The runtime deploys to the current Finland VPS as a systemd service using a root-owned immutable directory pinned to the merged Git SHA.
